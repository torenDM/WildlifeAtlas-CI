# AI Usage

При выполнении тестового задания использовался AI-инструмент ChatGPT.

## Использованный инструмент

- ChatGPT
- Модель: GPT-5.6 Sol

- Google AI Studio
- Модель: Gemini 3.1 Flash Lite

AI использовался как вспомогательный инструмент для планирования, изучения особенностей Swift/iOS, обсуждения архитектуры, подготовки части кода, тестов, комментариев и документации.
Результаты работы AI не принимались автоматически: код и предлагаемые решения проверялись, корректировались вручную и дополнительно проверялись через GitHub Actions.

## Для каких задач использовался AI

### 1. Организация работы и план разработки

ChatGPT использовался для обсуждения структуры проекта и разбиения тестового задания на последовательные этапы.
В частности, с AI обсуждались:
- последовательность реализации требований;
- структура каталогов;
- разделение Models / Networking / ViewModels / Views;
- порядок реализации pagination, filters, details и дополнительных возможностей;
- стратегия небольшого количества содержательных Git-коммитов;
- последовательность CI-проверок.

Используемый промпт:
> Разбей тестовое задание Wildlife Atlas на последовательные этапы разработки. Нужно использовать Swift, SwiftUI, MVVM, URLSession без сторонних библиотек. Разработка выполняется на Windows без Xcode, полноценная iOS-сборка будет проверяться через GitHub Actions. Не нужно дробить работу на слишком маленькие шаги.

### 2. Выбор среды разработки и способа тестирования

Так как локально у меня не было macOS и Xcode, я использовал ChatGPT для обсуждения возможного рабочего процесса.

В результате была выбрана схема:
- редактирование Swift-кода в Windows;
- локальная синтаксическая проверка доступных частей проекта;
- GitHub Actions с macOS runner и Xcode для полноценной сборки iOS-приложения;
- отдельный приватный CI-репозиторий для проверки изменений перед отправкой в репозиторий тестового задания.

Используемый промпт:

### 4. Изучение различий Kotlin и Swift

До выполнения задания у меня не было коммерческого опыта разработки на Swift.
При этом у меня был коммерческий опыт работы с Kotlin в ЭР-Телеком, поэтому значительная часть базовых концепций языка и подходов к разработке была знакома.

Kotlin и Swift имеют много схожих концепций, однако отличаются в важных деталях:
- optionals;
- value/reference semantics;
- property wrappers;
- Swift concurrency;
- SwiftUI state management;
- protocol-oriented подход;
- особенности `Codable`;
- работа с `@MainActor`;
- syntax Swift closures;
- особенности `NavigationStack`;
- interoperability между SwiftUI, Foundation и UIKit.

ChatGPT использовался как вспомогательный инструмент для изучения этих различий непосредственно во время разработки.

Используемый промпт:
> Я знаком с Kotlin, но раньше не разрабатывал коммерческие приложения на Swift. Объясняй Swift-конструкции через сравнение с Kotlin, особенно optionals, protocols, async/await, @MainActor, ObservableObject, @StateObject и SwiftUI state management.

### 5. Ручное редактирование `project.pbxproj`

Так как проект разрабатывался без локального Xcode, новые Swift-файлы нельзя было добавлять в Xcode project через интерфейс IDE.

Поэтому файл:
`WildlifeAtlas.xcodeproj/project.pbxproj`
приходилось изменять вручную.

ИИ использовался для подготовки и проверки необходимых изменений:
- `PBXBuildFile`;
- `PBXFileReference`;
- добавление файла в соответствующий `PBXGroup`;
- добавление файла в `PBXSourcesBuildPhase`.

Такой подход позволял снизить объем однообразной ручной работы, при которой легко допустить ошибку в идентификаторах или забыть добавить файл в одну из секций.

Один из используемых промптов:
> Я добавляю новый Swift-файл вручную без Xcode. Покажи точные изменения, которые необходимо внести в текущий project.pbxproj: PBXBuildFile, PBXFileReference, нужную PBXGroup и PBXSourcesBuildPhase. Не придумывай ID существующих объектов и опирайся только на текущий файл проекта.

## Предложения и результаты AI, которые были отклонены или исправлены

Во время разработки предложения AI не принимались как гарантированно корректные.
Были случаи, когда предложенные решения приходилось исправлять.

### Несуществующий метод `fetchObservations`
В одном из предложений AI использовал название метода:

```swift
fetchObservations(...)
```

хотя в реальном проекте сервис содержал:

```swift
observations(...)
```

Предложение было отклонено, потому что оно не соответствовало фактическому API текущего проекта.

После этого при дальнейшей работе изменения выполнялись только после проверки актуального содержимого соответствующего файла.

### Ошибка с `ObservationGridItemView`

В одном из вариантов кода для Grid AI ошибочно предложил структуру с именем:

```swift
ObservationRowView
```

вместо:

```swift
ObservationGridItemView
```
Это приводило бы к повторному объявлению типа. Ошибка была обнаружена и исправлена.

### Ручная работа с `project.pbxproj`

При работе с `project.pbxproj` несколько предложений требовали дополнительной проверки расположения идентификаторов и секций проекта.
Поэтому было принято правило: перед изменением `.pbxproj` сначала использовать актуальную версию файла и проверять все четыре элемента подключения нового Swift-файла:

1. `PBXBuildFile`;
2. `PBXFileReference`;
3. соответствующий `PBXGroup`;
4. `PBXSourcesBuildPhase`.

### Ошибка вывода типа `Set` в Favorites

При реализации удаления Favorites AI предложил код примерно следующего вида:

```swift
let ids = Set(
    offsets.compactMap { ... }
)
```

Swift compiler не смог вывести generic parameter `Element`.

GitHub Actions обнаружил ошибку:
```text
generic parameter 'Element' could not be inferred
```

Вместо усложнения типа решение было упрощено: элементы стали удаляться по индексам в обратном порядке. Этот вариант оказался проще и надежнее.

### Излишнее усложнение сохранения scroll position

Рассматривался вариант явного хранения scroll position через дополнительные SwiftUI API.
От него было решено отказаться, потому что текущая навигация через `NavigationStack` сохраняет экземпляр `ContentView` и его `@StateObject`.
Добавление отдельного механизма без подтвержденной проблемы усложнило бы код без очевидной необходимости.

## Как проверялись предложения AI

Для снижения риска ошибок использовались несколько уровней проверки:
- Сравнение результатов вывода в разных ветках ChatGPT и с разной формулировкой промптов
- Сравнение результата вывода с другой моделью (ChatGPT vs Gemini)
- Ручное ознакомление с результатом работы модели
- Проверка через GitHub Actions и appetize.io после реализации новых функций

### Проверка актуального кода

Перед изменением существующих файлов проверялось их текущее содержимое.
Это было особенно важно для:
- ViewModel;
- `INaturalistService`;
- Views;
- `project.pbxproj`.

### Локальная проверка

Там, где это было возможно в Windows, использовалась синтаксическая проверка Swift-файлов.
Также использовался:
```bash
git diff --check
```
для обнаружения проблем форматирования diff.

### GitHub Actions

Полноценная iOS-сборка выполнялась через Xcode на macOS runner.
После добавления тестов проект проверялся двумя независимыми CI-задачами:
- iOS Build;
- Unit Tests.
Изменения отправлялись в основной репозиторий после успешного прохождения проверок.

### Сервис appetize.io

В виду отсутствия возможности проверки через MacOS, использовалось онлайн-приложение, имитирующее ios-устройство.

## Итог

AI использовался как инструмент для ускорения планирования, обучения, подготовки шаблонного кода, тестов, комментариев, работы с `project.pbxproj` и документации.
При этом использование AI не исключало ручную проверку. Напротив, в процессе разработки несколько предложений AI были обнаружены как некорректные, исправлены и использованы как повод усилить процесс проверки актуального состояния проекта и CI.
